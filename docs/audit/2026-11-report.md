# Hallan portal audit — November 2026

Findings, with file and line context, are in [2026-11-findings.md](2026-11-findings.md). Short definitions of the abbreviations used below are in the glossary at the end.

## Overall verdict

**High.** The pages are public HTML. The damaging cases are a PIN checked in the browser, a password the page says is saved before the email code, a rota filtered only after the whole document has been downloaded, and a restaurant order that posts the price the browser is holding. None of these was proved against a live API response. The client is already written as if the API behaves that way, and the API source is not in this repository. There is no Critical finding, because a Critical here would mean a demonstrated exposure with no missing server check left to verify.

## Methodology and limits

Reviewed on 13 November 2026. The repository root is `/Users/dcs/Herd/HallanList`, starting from commit `15f78bb`. The review read the interactive pages (`home.html`, `index.html`, the staff portal, management, rota, clock, picking sheets, the timesheet mock, and the PDF snippet) and searched them for API calls, tokens, and HTML insertion. The multi-megabyte flyer files were sized and not read line by line.

One live check: an unauthenticated `GET` of `https://portal.hallans.co.uk/` returned `200` from GitHub Pages, with `cache-control: max-age=600` and `access-control-allow-origin: *`, and without the security headers named in SEC-12. No login was attempted. No request was sent that would change data.

Not reviewed: the Render API source, its database, its backups, its CORS rules, its rate limits, its password hashing, and whether it actually returns PINs or commits a password before the email code. Those are open questions, not passes. The trade-account site linked from the home page is a different repository. Search ranking and translation were out of scope.

## Critical

None.

## High — with suggested fixes

**SEC-1 and PRIV-2.** The clock downloads the rota and compares PINs in the page. The schedule stores those PINs in the same document and shows them in a text field. Stop returning PINs. Check the PIN on the API and return only that person's name and today's punches.

**SEC-2.** The clock's instructions tell a manager to leave their own rota token on the shared till. Replace that with a device credential that can write only the punch just verified.

**SEC-3.** After a forgotten-password call, the staff page tells the person the new password is already saved, and only then asks for the email code. The department list used as the other input is public. On the API, keep the old password until the code succeeds.

**SEC-4.** The schedule hides tabs using `rota_role` and `rota_login_id` from the browser, after downloading the whole rota, and saves the whole document back. Filter the read and reject writes outside the caller's departments.

**ADV-1.** Submitting a restaurant order posts the cart, including `trade_price`. A custom line is sent with a null price. Price stock lines on the server, and do not confirm a custom line at zero.

**CONF-1.** Every hostname except `localhost` and `127.0.0.1` calls the live API. A file opened from disk does too. Development and a mistaken click can change production prices and passwords. Send non-production hostnames to a non-production API.

**A11Y-1.** The picking and management sign-in fields have placeholders and no labels. High under WCAG 2.2 AA — not a commercial-secrecy or data-isolation blocker. Sequence it after the PIN, password, rota, and price fixes unless Hallan has committed to AA on a date.

## Medium

- **SEC-5.** Picking tiles are hidden from a module list stored in the browser. The API must enforce the module on each route, including invoices (ADV-3).
- **SEC-6.** The wholesale and Manage-Customers passwords are checked once in a prompt. Later reads use only the portal token. The client allows a four-character wholesale password.
- **SEC-7.** The picking timer posts seconds to a list id with no bearer token.
- **SEC-8.** The PDF snippet writes filenames and URLs into HTML without escaping.
- **SEC-9.** The rota writes employee names and time-off reasons into HTML without escaping. The staff portal does escape.
- **SEC-10.** The staff token is kept in `localStorage` until sign-out. Server expiry was not visible.
- **PRIV-1.** No privacy notice, copy, or deletion path is in the product. This is a process gap, not legal advice.
- **PRIV-3.** Holiday spreadsheets are parsed by SheetJS from a CDN, and the pages load Google Fonts. The Facebook script is loaded only when WhatsApp signup is used, and the page already warns that it can read the token.
- **A11Y-2.** Holiday dialogs do not trap focus or close on Escape.
- **DATA-1.** Holiday "days requested" is free text, not a value derived from the dates.
- **DATA-2.** A holiday upload creates unknown employees unless someone unticks the box.
- **DATA-3.** Blocking wholesale prices sends the numbers currently on screen.
- **BUG-1.** The clock still builds the date with `toISOString()`, which the schedule has already stopped doing because it shifts the day during British Summer Time.
- **BUG-3.** `timesheet/index.html` shows sample hours and does not call an API. The buttons look real.
- **BUG-4.** The PDF snippet reads `portal_token`. The app stores `hallan_portal_session`.
- **PERF-1.** `wholesale-flyer.html` is 4.4 MB. The vegetable flyer is 618 KB.
- **PERF-2.** `picking-sheets/index.html` is 1.3 MB and references four CDN libraries on every visit.
- **CONF-2.** There is no error tracker and no backup note in this repo. Admin URLs are public. The API is the only gate.
- **DEP-1.** CDN scripts have versions in the URL, no lockfile, and no integrity hash. SheetJS 0.18.5 has had security reports since that release. No exploit was re-run.
- **TEST-1.** There are no tests and no workflow. A push to GitHub Pages is the release.
- **ADV-2.** Holiday history takes `employeeId` from the query string. HR and staff share the path.
- **ADV-3.** Invoice lines, including prices, are saved from the grid the operator edited.

## Low

- **SEC-11.** The new management password is `type="text"`.
- **SEC-12.** The live home page response has no content-security policy, HSTS, frame control, nosniff, or referrer policy. GitHub Pages is not giving this repo a way to set them.
- **PRIV-4.** Tokens and a customer name sit in `localStorage` until that app signs out.
- **A11Y-3.** Several pages have no `<main>` and no skip link. The home logo has alt text. Zoom is not disabled.
- **BUG-2.** `index.html` says it is sending you to the vegetable flyer, then opens the portal, and links to `/home/`, which does not exist.
- **BUG-5.** The staff role dropdown is not sent. People can think they are choosing HR.
- **BUG-6.** The home page says restaurant orders are coming soon. The picking app already has them.
- **PERF-3.** SheetJS loads on the staff sign-in page, and the rota loads PDF libraries for people who may never export.
- **QUAL-1.** The picking app, the rota, and the staff portal are single files, with the API host copied into each. No `TODO` or `FIXME` comments were found.

## Residual risk

Accepted in [00-security.md](../00-security.md), and not raised again as defects:

- The department list is public. It identifies a row. It is not a secret. The email code is the proof.
- Published flyer HTML and PDFs may contain product prices Hallan has chosen to show. They must not contain staff or customer data.
- This is one business, not a multi-tenant product.
- GitHub Pages may keep serving the UI without the headers in SEC-12 until the host changes. That is a known limit of the current host, not a reason to store tokens in the HTML.
- A shared wholesale password may continue to exist. SEC-6 stands until the API checks it on every price read. The document does not accept a prompt in the page as that check.

Backups and point-in-time recovery were not visible. They remain an operational risk until the API host is reviewed, not a finding with a file to point at.

## Open questions

- Does `GET /api/staff/rota-state` currently include `pin`? The clock will not work unless it does, or unless some other field is being compared by mistake.
- Does `POST /api/staff/forgot-password` replace the hash before the code is accepted?
- Does the API trim `rota-state` and holiday history by role, or return whatever the token asks for?
- What is the server token lifetime for `hallanStaffToken` and `rota_token`?
- What is the backup window on the Render database?
- Does restaurant submit ignore `trade_price` and price from `stockid`?

## Appendix — operations

- Deploying the UI is a git push to `19999vahira/HallanList`. GitHub Pages serves `main` (the branch this audit committed docs onto) at `portal.hallans.co.uk`. There is no review workflow in the repo.
- The clock comment says the borrowed token lasts about twelve hours. Someone has to sign in on the till again after that. That chore goes away if SEC-2 is done.
- Any signed-in shelf-check user can create another management user. The new password is visible while typing (SEC-11).
- Deleting a zone or a location asks for confirmation and says the check history goes with it. The API's actual cascade was not seen.
- The home page links to a trade-account form on another GitHub Pages site. That site was not audited.
- Who does what: HR owns holiday uploads and rota grants. Portal admins own picking users and the IP list. A named owner for management users is not defined in the pages.

## Appendix — legal and process

Not legal advice. There is no privacy notice and no terms link on the portal (PRIV-1). Holiday and clock data are employment records. Restaurant names and orders are customer records. A copy or deletion request has to be handled by someone with API database access. Nothing in this repository records that request.

## Glossary

- **ADV.** A finding from the adversarial pass, which looked for price and identity holes the category lists can miss.
- **A11Y.** An accessibility finding against WCAG 2.2 AA.
- **API.** The Render service at `hallan-picking-backend.onrender.com`. It is not in this repository.
- **Bearer token.** The secret the browser sends in the `Authorization` header after login. Each app stores its own.
- **BUG.** A behaviour that is wrong even aside from security, such as the UTC clock date.
- **CDN.** A third-party host the pages load libraries from, here mostly cdnjs.
- **CONF.** A configuration finding, such as the missing staging API.
- **CSP.** Content-Security-Policy, a response header that limits which scripts a page may run.
- **DATA.** A finding about the shape of data the browser sends.
- **DEP.** A dependency finding.
- **DKIM.** A DNS record that lets receivers check that a message really came from the sending domain.
- **GDPR.** The UK and EU rules on personal data. This report records process gaps. It is not a legal opinion.
- **High (WCAG).** A serious accessibility failure. The triage note on A11Y-1 means it is not treated as a data leak.
- **HSTS.** Strict-Transport-Security, a header that tells browsers to keep using HTTPS.
- **HR.** The staff role that may see and decide everyone's holidays.
- **IDOR.** A request where changing an id returns or edits someone else's row. ADV-2 is that shape if the API does not check the role.
- **PERF.** A payload or loading finding.
- **PIN.** The short code the clock asks for. It is a secret. It is not the staff password.
- **PITR.** Point-in-time recovery, restoring a database to an earlier moment. Not verified.
- **PRIV.** A privacy finding.
- **QUAL.** A code-structure finding.
- **SEC.** A security finding.
- **SPF.** A DNS record listing which servers may send mail for a domain.
- **TEST.** A finding that a check is missing.
- **WCAG.** The Web Content Accessibility Guidelines, version 2.2, level AA, used for the accessibility pass.
